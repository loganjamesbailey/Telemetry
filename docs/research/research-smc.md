# smc

## Summary
On Apple Silicon (M1), all thermal/fan telemetry and control flows through two mechanisms. (1) The AppleSMC IOKit user client: open with IOServiceOpen on the service matched by IOServiceMatching("AppleSMC"), then issue IOConnectCallStructMethod with selector 2 (KERNEL_INDEX_SMC) and an 80-byte SMCKeyData_t struct whose data8 field selects the operation (9=read key info, 5=read bytes, 6=write bytes, 8=read key by index). Keys are 4-char ASCII packed big-endian into a UInt32. On M1 the fan keys F0Ac/F0Mn/F0Mx/F0Tg are all type "flt " (4-byte little-endian IEEE-754 float, RPM) and F0Md (mode) is ui8 (0=auto, 1=forced; thermalmonitord holds 3="system mode" on newer chips); the Intel-era fpe2 encoding and the "FS! " bitmask are NOT used on Apple Silicon. Reads need no privileges; writes require root (kIOReturnNotPrivileged otherwise) — SIP does not interfere, no special entitlement exists, but App Sandbox blocks IOServiceOpen, so the app must be distributed outside the Mac App Store and use a small root helper (SMAppService.daemon + NSXPC with codesign peer validation, as Stats does). On M1 specifically, writing F0Md=1 directly as root works; on M3/M4 firmware rejects it with SMC result 0x82 until the "Ftst" key is written to 1 (then wait ~3-6 s for thermalmonitord to yield, retrying). The robust sequence used by current Stats on all arm64: probe whether the mode key is "F0Md" or lowercase "F0md"; try direct mode write; on failure use Ftst unlock; then write F0Tg as a float, with a retry loop because writes fail transiently and because IOKit can return success while the SMC result byte is non-zero (must check output.result==0). Restore automatic control by writing Ftst=0 (M1-M4) and/or F0Md=0 + F0Tg=0.0. Sleep resets Ftst to 0 and cancels manual control, so forced mode must be re-applied ~3 s after wake (Stats sets auto before sleep and re-applies after wake); reboot always returns fans to automatic. (2) Temperatures: the SMC exposes M1 per-core keys (Tp01/Tp05/Tp0D/Tp0H/Tp0L/Tp0P/Tp0X/Tp0b P-cores; Tp09/Tp0T E-cores; Tg05/Tg0D/Tg0L/Tg0T GPU; Tm02/06/08/09 memory; Tc0a/b/x/z aux), while the private IOHIDEventSystemClient route (matching PrimaryUsagePage 0xff00, PrimaryUsage 5, event type 15=kIOHIDEventTypeTemperature, value via IOHIDEventGetFloatValue(event, 15<<16)) yields far better-named coverage on M1 ("PMU tdie%", "pACC/eACC MTR Temp Sensor%", "GPU MTR Temp Sensor%", "SOC MTR Temp Sensor%", "ANE MTR Temp Sensor%", "NAND CH% temp", "gas gauge battery") with no privileges; the best app design (what Stats ships) reads both and merges them, and uses SMC only for fans and writes.

## Key facts
- Opening the SMC (all four projects identical): IOServiceGetMatchingServices(kIOMainPortDefault, IOServiceMatching("AppleSMC")) -> IOIteratorNext -> IOServiceOpen(device, mach_task_self_, 0, &conn). Every operation is IOConnectCallStructMethod(conn, 2 /*kernelIndex*/, &input, size, &output, &size) where input/output are an 80-byte SMCKeyData_t {key: UInt32, vers, pLimitData, keyInfo{dataSize: IOByteCount32, dataType: UInt32, dataAttributes: UInt8}, padding: UInt16, result: UInt8, status: UInt8, data8: UInt8, data32: UInt32, bytes: 32-byte tuple}. Sources: exelban/stats SMC/smc.swift, hholtmann/smcFanControl smc-command/smc.c, beltex/SMCKit SMCKit/SMC.swift, narugit/smctemp smctemp.h (kKernelIndexSmc=2).
- Selector bytes go in input.data8: 5 = read bytes (kSmcCmdReadBytes), 6 = write bytes, 8 = read key by index (for enumerating all keys via the '#KEY' count), 9 = read key info. A read is two calls: first data8=9 to get dataSize+dataType, then data8=5 to get bytes. SMC keys are 4-char ASCII packed big-endian: str.utf8.reduce(0){ $0 << 8 | UInt32($1) }.
- CRITICAL write gotcha (Stats SMC/smc.swift write()): IOConnectCallStructMethod can return kIOReturnSuccess while the firmware rejected the write — you MUST check output.result == 0x00; non-zero (e.g. 0x82 kSMCBadCommand) means the write was silently dropped. This is the 'half-writes ignored' quirk.
- M1 fan keys and types (MacBookPro17,1 has one fan, id 0): FNum (ui8, fan count=1), F0Ac actual RPM, F0Mn min, F0Mx max, F0Tg target — all type "flt " = 4-byte little-endian IEEE-754 float on Apple Silicon (Intel used fpe2: UInt16 with 2 fractional bits). F0Md mode is ui8: 0=automatic, 1=forced/manual, 3=system-managed (thermalmonitord's default hold on newer chips; Stats models it as FanMode.auto3). The Intel 'FS! ' global bitmask and F0ID fan-name key ({fds struct) are Intel-era; F0ID may be absent on M1 (Stats falls back to 'Fan #0').
- Fan mode key case varies by chip: Stats probes 'F0md' (lowercase) at init — lowercase exists on M5+, M1 uses capital 'F0Md'. fanModeKey(): if read of 'F0md' succeeds with dataSize>0 use 'F(id)md' else 'F(id)Md'.
- Privileges: SMC reads (selector 5/9/8) work as a normal user with no entitlements. SMC writes require root — non-root gets kIOReturnNotPrivileged (SMCKit throws SMCError.notPrivileged on it). SIP does NOT block root SMC writes; no private entitlement is needed; there is no kext. BUT App Sandbox denies iokit-open on AppleSMC, so the app must be direct-distributed (not Mac App Store).
- How Stats gets root: a ~100 KB privileged helper 'eu.exelban.Stats.SMC.Helper' embedded at Contents/Library/LaunchServices/, registered via SMAppService.daemon(plistName:) on macOS 13+ (legacy SMJobBless fallback with kSMRightBlessPrivilegedHelper), talking NSXPC (machServiceName, .privileged) with both sides validating the peer's code-signing certificates (CodesignCheck comparing audit-token cert chains). Helper executes the bundled 'smc' CLI as root: 'smc fan 0 -m 1', 'smc fan 0 -v 3000', 'smc reset'. Files: Kit/helpers.swift (SMCHelper client, lines ~1047-1290), SMC/Helper/main.swift, SMC/Helper/Launchd.plist.
- M1 forced-fan write path: on M1, writing F0Md=1 directly as root WORKS without any unlock — agoodkind/macos-smc-fan research.md: 'Direct writes to F%dMd=1 are confirmed to work on the tested M1 machine without the Ftst unlock.' From M3/M4 on, thermalmonitord holds F0Md=3 and firmware rejects mode writes with SMC result 0x82 until you write Ftst=1 (ui8 'force test' diagnostic key), wait ~3-6 s for F0Md to fall to 0, then retry F0Md=1. Current Stats unlockFanControl() runs on all arm64: try direct F0Md=1; on failure read Ftst, write Ftst=1 (writeWithRetry up to 100 attempts), usleep(3_000_000) 'Wait for thermalmonitord to yield control', then retry mode write up to 300 attempts at 100 ms intervals.
- setFanSpeed flow (Stats SMC/smc.swift): clamp requested speed to F0Mx; read the mode key and if bytes[0] != 1 run unlockFanControl; read F0Tg to discover its dataType; if "flt " copy Float(speed) little-endian bytes into bytes[0..3] (if fpe2: bytes[0]=speed>>6, bytes[1]=(speed<<2)^((speed>>6)<<8)); write with writeWithRetry (default 10 attempts, 50 ms apart — transient failures are normal on Apple Silicon).
- Restoring automatic control: Stats resetFanControl() writes Ftst=0 if the key exists and is 1 (this alone hands fans back to thermalmonitord on M1-M4); if Ftst is absent (M5+) it writes F(i)md=0 for every fan from FNum. setFanMode(id, .automatic) also writes F0Md=0 then F0Tg=0.0. Stats resets all forced fans to automatic in Module.willTerminate() — your app must do the same on quit and ideally have the root helper watchdog the app connection.
- Sleep/wake/reboot: SMC firmware (RTKit) resets Ftst to 0 during sleep transitions; manual control is lost on wake and must be re-established. Stats' strategy (Modules/Sensors/popup.swift lines 824-862): on NSWorkspace.willSleepNotification save current mode/speed and set the fan to automatic; on didWakeNotification wait 3 s then re-apply mode and speed. Reboot always returns full automatic control (exelban/stats issue #2538: manual settings never survive reboot — re-apply at app launch).
- Minimum-RPM enforcement is soft, not hard (agoodkind research on Apple Silicon): target can be set to 0 RPM (fan stops), below reported F0Mn (spins at lowest achievable), or above F0Mx. So the app's own UI must clamp to [F0Mn, F0Mx] for safety — firmware will not save you.
- M1 SMC temperature keys (all readable unprivileged, type flt, degrees C) — from narugit/smctemp smctemp.h+smctemp.cc M1 branch and exelban/stats values.swift 'Apple Silicon' section: P-cores Tp01, Tp05, Tp0D, Tp0H, Tp0L, Tp0P, Tp0X, Tp0b; E-cores Tp09, Tp0T; GPU Tg05, Tg0D, Tg0L, Tg0T (plus Tg1b, Tg4b seen on M1 mini); memory Tm02, Tm06, Tm08, Tm09; aux CPU die Tc0a, Tc0b, Tc0x, Tc0z; plus generic TA%P ambient, TW0P airport, battery TB1T (Intel-tagged in Stats). Full key enumeration: read '#KEY' for total count then selector 8 (readIndex) per index — filter keys starting with 'T' whose type is flt/sp78/ui8.
- IOHIDEventSystemClient temperature route (better names + more coverage on M1, no root, but PRIVATE API): declare prototypes by hand (bridge.h in Stats / temp_sensor.m in fermion-star/apple_sensors): IOHIDEventSystemClientCreate(kCFAllocatorDefault); IOHIDEventSystemClientSetMatching(client, {"PrimaryUsagePage": 0xff00 (kHIDPage_AppleVendor), "PrimaryUsage": 5 (kHIDUsage_AppleVendor_TemperatureSensor)}); IOHIDEventSystemClientCopyServices(); per service: name = IOHIDServiceClientCopyProperty(service, CFSTR("Product")), event = IOHIDServiceClientCopyEvent(service, kIOHIDEventTypeTemperature /*=15*/, 0, 0) (may be NULL — skip), value = IOHIDEventGetFloatValue(event, IOHIDEventFieldBase(15) /*= 15<<16*/). Voltage/current sensors: page 0xff08 usage 3/2 with kIOHIDEventTypePower=25.
- M1 HID sensor names observed (Stats HIDSensorsList in values.swift + apple_sensors): 'pACC MTR Temp Sensor%' (P-core), 'eACC MTR Temp Sensor%' (E-core), 'GPU MTR Temp Sensor%', 'SOC MTR Temp Sensor%', 'ANE MTR Temp Sensor%' (Neural Engine), 'ISP MTR Temp Sensor%', 'PMGR SOC Die Temp Sensor%', 'PMU tdie%' / 'PMU tdev%', 'gas gauge battery', 'NAND CH% temp'. Stats computes 'Average SOC'/'Hottest SOC' from the SOC MTR values and discards readings outside 0..110 C. Verdict: HID route gives the best names and per-block coverage on M1; SMC route is still required for fans and is the only writable interface.
- Exact source files to crib from: exelban/stats — SMC/smc.swift (full SMC client + arm64 fan control incl. Ftst), SMC/main.swift (CLI: fan/fans/set/reset commands), SMC/Helper/main.swift (root XPC helper), Kit/helpers.swift (SMAppService/SMJobBless install + XPC client), Modules/Sensors/readers.swift (sensor+fan reader, loadFans via FNum/F(i)ID/F(i)Mn/F(i)Mx/F(i)Ac), Modules/Sensors/reader.m + bridge.h (AppleSiliconSensors HID bridge), Modules/Sensors/values.swift (key->name tables); narugit/smctemp — smctemp.h (per-chip key constants), smctemp.cc (M1 averaging + keyinfo cache + read-by-index); hholtmann/smcFanControl — smc-command/smc.c (canonical C struct layout, Intel-era); beltex/SMCKit — SMCKit/SMC.swift (clean Swift SMCParamStruct + error mapping, Intel-era); fermion-star/apple_sensors — temp_sensor.m (minimal HID route); agoodkind/macos-smc-fan docs/research.md (M1-M5 Ftst research, error codes, sleep behavior).

## Recommendations
- Architecture: split into (a) an unprivileged app process doing all reads — SMC reads for fan RPM (F0Ac/F0Mn/F0Mx/F0Tg/F0Md) and T-keys, plus the IOHID route for nicely-named sensors — and (b) a tiny root helper registered with SMAppService.daemon(plistName:) exposing setFanMode/setFanSpeed/reset over NSXPC with code-signing peer validation on both ends (copy Stats' CodesignCheck approach). Do not sandbox either binary.
- Implement the write path exactly as current Stats does for arm64: probe mode-key case ('F0md' vs 'F0Md'), attempt direct F0Md=1 first (sufficient on M1), fall back to Ftst=1 -> wait 3 s -> retry mode write (100 ms interval, generous timeout); wrap every write in a retry loop and treat output.result != 0 as failure even when IOKit says success; verify by reading back F0Md/F0Tg and watching F0Ac converge.
- Safety rails (the firmware won't enforce them): clamp all user-set targets to [F0Mn, F0Mx]; reset to automatic (Ftst=0 / F0Md=0) on app quit, XPC invalidation, and before sleep; re-apply forced mode ~3 s after didWakeNotification and at app launch (nothing persists across reboot); add a temperature kill-switch that restores automatic control if any die sensor exceeds ~95-100 C while a manual curve is active.
- For the sensor browser, enumerate SMC keys dynamically ('#KEY' + selector 8) instead of hardcoding, then overlay the known M1 name tables (Stats values.swift, smctemp.h) and the HID 'Product' names; decode by the dataType string returned from key info (flt /sp78/fpe2/ui8/ui16/ui32) rather than assuming a type per key.
- Build fan curves on the HID/SMC die temperatures (e.g. average of Tp0*/PMU tdie, or 'Hottest SOC') with hysteresis and a minimum dwell time between target changes; write F0Tg no more often than every few seconds to avoid fighting the firmware and burning writes.
- Prototype risk-free first: all reads (both routes) need no privileges, so build the full telemetry UI before touching writes; test writes with the Stats-bundled 'smc' CLI (sudo smc fan 0 -m 1 / -v RPM / smc reset) on the target M1 before writing your own helper.

## Gotchas
- IOConnectCallStructMethod returning kIOReturnSuccess does NOT mean the write happened — the SMC result byte (output.result) must be 0x00; thermalmonitord-protected keys fail with 0x82 (kSMCBadCommand). Older projects (smcFanControl, SMCKit) never check this and will appear to work while doing nothing.
- SMCKit and smcFanControl are Intel-era: they assume fpe2 fan values and the 'FS! ' mode bitmask, both wrong on M1 (flt floats, per-fan F0Md ui8). Use them only for struct layout/constants, not fan logic.
- SMC writes on Apple Silicon fail transiently even as root — a single write attempt is unreliable; Stats retries 10x at 50 ms for normal writes, up to 300x at 100 ms after an Ftst unlock.
- Leaving Ftst=1 (or F0Md=1) while your app crashes leaves the machine without system fan management — the OS will not reclaim control until sleep or reboot. Handle SIGTERM/SIGINT, XPC invalidation, willSleep, and willTerminate by restoring automatic mode.
- Sleep silently resets Ftst to 0 and kills manual control; wake requires the full unlock+re-apply sequence (wait ~3 s after didWakeNotification). Nothing survives reboot.
- The fan-mode key is lowercase 'F0md' on some chips (M5+) and 'F0Md' on M1 — probe at startup like Stats' fanModeKey() instead of hardcoding.
- IOHIDEventSystemClientCreate / IOHIDServiceClientCopyEvent / IOHIDEventGetFloatValue are private APIs (hand-declared prototypes); fine for a free direct-distributed app, disqualifying for the Mac App Store — as is the unsandboxed AppleSMC access itself.
- IOHIDServiceClientCopyEvent can return NULL for some matched services — always nil-check before IOHIDEventGetFloatValue, and filter garbage readings (Stats keeps only 0..110 C).
- Firmware does NOT clamp fan targets to the reported minimum on Apple Silicon — you can set 0 RPM and stop the fan entirely; enforce F0Mn in your own UI.
- SMJobBless (legacy helper install) requires a paid Developer ID certificate; SMAppService.daemon (macOS 13+) is the modern path and needs user approval in System Settings > Login Items; for purely personal use you can instead load the helper plist manually with launchctl as root.
- kIOMasterPortDefault is deprecated — use kIOMainPortDefault (macOS 12+), as current Stats does.
- MacBookPro17,1 has exactly one fan (FNum=1, keys F0*), and F0ID (fan name) may not exist on Apple Silicon — fall back to a generic name.

## Verification
- [CONFIRMED] All SMC operations go through IOConnectCallStructMethod with kernel selector 2 on an 80-byte struct, with the operation chosen by data8: 5=read bytes, 6=write bytes, 8=read key by index, 9=read key info.
- [CONFIRMED] IOConnectCallStructMethod can return kIOReturnSuccess while the SMC firmware silently rejected the write, so the implementation must check output.result == 0x00; 0x82 (kSMCBadCommand) is the firmware rejection seen on thermalmonitord-protected fan-mode keys.
- [CONFIRMED] On Apple Silicon the fan speed keys (F0Ac/F0Mn/F0Mx/F0Tg) are 4-byte float type 'flt ' (fpe2 is Intel-era), F0Md is ui8 with 0=automatic, 1=forced, 3=system-managed, and the mode key case must be probed at runtime ('F0md' lowercase on newer chips vs 'F0Md'); writes need retry loops (Stats: writeWithRetry default 10 attempts/50ms, Ftst write up to 100 attempts, post-unlock mode write up to 300 attempts at 100ms after a 3s usleep).
- [CONFIRMED] SMC reads work from an unprivileged process while fan-control writes require root (kIOReturnNotPrivileged otherwise), so the app needs a privileged helper; Stats implements this with SMAppService.daemon(plistName:) registering a helper embedded at Contents/Library/LaunchServices/, NSXPCConnection(machServiceName:, options: .privileged), codesign peer validation via audit-token certificate comparison, and a legacy SMJobBless fallback.
  - CORRECTION: One detail is misplaced: the CodesignCheck struct (auditToken(for:), codeSigningMatches comparing certificate chains) lives in SMC/Helper/main.swift, not Kit/helpers.swift. Also note the 'App Sandbox blocks IOServiceOpen on AppleSMC' sub-claim was not independently verified against an Apple primary source (though Stats and all comparable apps ship unsandboxed).
- [CONFIRMED] On the tested M1, writing F0Md=1 directly as root works without the Ftst unlock (Ftst=1 -> ~3-6s wait -> retry is the fallback needed on M4-class machines); SMC firmware (RTKit) resets Ftst to 0 during sleep so manual control must be re-applied after wake; and the reported minimum RPM is a guideline not enforced by firmware — targets of 0 RPM or below F0Mn are accepted, so the app must clamp in its own UI.
  - CORRECTION: Caveat, not refutation: the M1 direct-write evidence is a single tested machine (MacBook Pro M1 Pro, MacBookPro18,1 — not the plan's MacBookPro17,1), and Stats' own code comments label the Ftst path as 'M1-M4' with direct mode 'works on M5+'. The two-phase sequence (try direct F0Md=1 first, fall back to Ftst unlock) is what both primary sources actually implement and is the safe design regardless of which reading is right for MacBookPro17,1.
- [CONFIRMED] The unprivileged IOHID temperature route on M1 matches services with PrimaryUsagePage 0xff00 and PrimaryUsage 5, copies events of type kIOHIDEventTypeTemperature = 15, and reads the value via IOHIDEventGetFloatValue(event, IOHIDEventFieldBase(15)) where IOHIDEventFieldBase(type) = type << 16.
