# arch

## Summary
For a 2025–2026 thermal/fan-control menu bar app on macOS 14–26, the consensus architecture is: LSUIElement accessory app; a hybrid menu bar presence (SwiftUI MenuBarExtra with .window style for the popover, plus MenuBarExtraAccess or a raw NSStatusItem when you need dynamic label rendering like live RPM text + sparkline — this is exactly what Stats does with custom NSViews added to statusItem.button); a separate SwiftUI Window scene for the dashboard (avoid the Settings scene / openSettings path, which is broken on Tahoe 26); @Observable (Observation framework, macOS 14+) as the single state store; sensor polling on a background DispatchSourceTimer with ~10% leeway and adaptive cadence, publishing snapshots to the MainActor; Swift Charts with a fixed-size ring buffer (~300–600 visible points) and macOS 15's vectorized LinePlot when available; SMAppService.mainApp for launch-at-login; Sparkle 2 via SPM with EdDSA-signed appcast for free distribution. Recommended deployment target: macOS 14 minimum (macOS 15 if you want vectorized plots unconditionally); supporting macOS 13 costs @Observable, openSettings, and chart interaction APIs for an EOL'd OS.

## Key facts
- MenuBarExtra (macOS 13+) has two styles: .menu (default, NSMenu-like) and .window (anchored chrome-less panel). The .menu style BLOCKS THE RUN LOOP while the menu is open — bindings don't update and you cannot programmatically dismiss it; the .window style is required for any live-updating popover content. Confirmed by orchetect/MenuBarExtraAccess README and Apple feedback FB11984872.
- First-party MenuBarExtra still has NO API (as of Xcode 26) to: programmatically show/hide the presented window, access the underlying NSStatusItem or NSWindow, or handle right-click. orchetect/MenuBarExtraAccess (macOS 13+, no private API, Mac App Store safe) adds an isPresented Bool binding, NSStatusItem access, and NSWindow access for .window style via .menuBarExtraAccess() scene modifier and .introspectMenuBarExtraWindow() view modifier.
- MenuBarExtra's label ViewBuilder only renders Text and Image — SF Symbol size/font customization is OS-controlled and arbitrary views are ignored. Live-updating Text in the label DOES work (label re-renders on state change; historic bugs were in .menu-style content, not the label). A menu-bar sparkline therefore must be pre-rendered to an Image (ImageRenderer or NSImage drawing) each tick, or you drop to NSStatusItem with a custom view.
- Stats (exelban/stats), the reference implementation for live menu-bar telemetry, uses NSStatusItem + custom NSView subclasses, not MenuBarExtra: Kit/module/widget.swift defines a widget_t enum (mini, lineChart, barChart, speed, sensors...), a WidgetWrapper NSView base class, and SWidget which creates NSStatusBar.system.statusItem(withLength:) and does menuBarItem?.button?.addSubview(widgetView), resizing via a setWidth() callback. This is the proven pattern for drawing live RPM/temp text and tiny charts directly in the menu bar with variable width.
- Opening the SwiftUI Settings scene from a menu bar app is broken territory (Peter Steinberger, June 2025, steipete.me): private selectors showSettingsWindow:/showPreferencesWindow: are dead since macOS 14; SettingsLink is unreliable inside MenuBarExtra; the openSettings environment action works on macOS 15 but does NOT work on macOS Tahoe 26. The working macOS 14+ recipe needs a hidden Window scene declared BEFORE the Settings scene, toggling NSApp.setActivationPolicy(.accessory → .regular), 100–200 ms Task.sleep delays, and NSApp.activate — scene declaration order genuinely affects whether it works. Practical takeaway: skip the Settings scene entirely and put preferences in your own dashboard Window scene.
- Dock-icon-less operation: set LSUIElement = YES ('Application is agent (UIElement)') in Info.plist. macOS won't let a window properly become key/front while the app is .accessory, so the standard pattern is: on dashboard-window open, NSApp.setActivationPolicy(.regular) + NSApp.activate; on last-window-close revert to .accessory. Use a single SwiftUI Window scene (macOS 13+) with openWindow, not WindowGroup, so only one dashboard instance exists.
- Swift Charts performance: naive per-point ForEach LineMark degrades badly past ~1–2k points (Apple forums threads 728636, 763757 report UI unresponsiveness in real-time updates). Best practice: fixed-capacity ring buffer, downsample to ~300–600 visible points (min/max decimation per pixel bucket), fixed/explicit chartYScale domain to avoid re-layout, and .drawingGroup for rasterized compositing. macOS 15+ adds vectorized plots — LinePlot/AreaPlot/BarPlot etc. (WWDC24 session 10155) — designed to efficiently handle 1000+ points from a plottable collection; chartXSelection and chartScrollableAxes need macOS 14+. At a 1–2 s sample cadence, 60 fps is only about chart-interaction smoothness, not data rate — updates themselves are trivially cheap if the buffer is bounded.
- Efficient polling (Apple Energy Efficiency Guide for Mac Apps): give every repeating timer a tolerance (~10%) so the system can coalesce wakeups — untolerated timers materially hurt idle residency; use DispatchSourceTimer with leeway on a .utility QoS queue. IOKit/SMC reads must never run on the main thread — read on the background queue, then hop to MainActor to mutate the @Observable store. Adaptive cadence pattern: ~1 s while popover/dashboard visible, ~5 s when only the menu-bar label shows, suspend on NSWorkspace.screensDidSleepNotification / display sleep, and gate dashboard work on NSWindow.occlusionState (applicationDidChangeOcclusionState + NSApplicationOcclusionStateVisible) since Apple's guide says to halt work the moment windows are occluded.
- @Observable (Observation framework, macOS 14+) is the 2025 default over ObservableObject/Combine: views invalidate only on properties they actually read (an ObservableObject with 10 @Published properties redraws every observer on any change), it works with plain @State/@Environment instead of @StateObject/@EnvironmentObject, and it removes the Combine dependency entirely. For this app: one @Observable SensorStore with fanRPM/temps/history is sufficient; no Combine needed anywhere.
- Launch at login: SMAppService.mainApp (macOS 13+, ServiceManagement) — try SMAppService.mainApp.register() / .unregister(); user gets a system notification when added. Always read SMAppService.mainApp.status live (never cache in UserDefaults) because users can remove the login item in System Settings at any time; handle .requiresApproval by deep-linking with SMAppService.openSystemSettingsLoginItems().
- Sparkle 2 (github.com/sparkle-project/Sparkle) is the standard free-app update path: add via SPM, instantiate SPUStandardUpdaterController (programmatic setup for SwiftUI, wire 'Check for Updates…' via canCheckForUpdates), sign updates with EdDSA using generate_appcast over your archive folder, host appcast.xml + zips on GitHub Releases/Pages. App must be Developer ID signed + notarized. Non-sandboxed apps (which this must be anyway — SMC access and a privileged fan-control helper preclude sandboxing) skip Sparkle's XPC-service sandbox configuration entirely.
- Deployment target trade-offs: macOS 13 (Ventura, security-EOL since late 2025) has MenuBarExtra, Window scene, Swift Charts basics, SMAppService — but lacks @Observable, openSettings, SettingsLink, chartXSelection/chartScrollableAxes. macOS 14 (Sonoma) unlocks all of those and is what comparable apps require (Ice requires macOS 14 'due to system APIs available starting in 14'; Loop supports 13+). macOS 15 (Sequoia) adds vectorized LinePlot/AreaPlot and better window placement. Every Apple Silicon Mac that can run 14 can run 15/26, so raising the floor to 14–15 excludes almost no Apple Silicon users; the target M1 machine is on 26.5.
- macOS 26 Tahoe specifics: menu bar is fully transparent under Liquid Glass — status item icons must be template images / SF Symbols to adapt to wallpaper-through backgrounds; glass effects are automatic with no NSVisualEffectView work. Tahoe broke many menu-bar-manager assumptions (Bartender/Ice/Barbee): NSStatusItem.isVisible can return true while the icon is actually hidden behind the notch or pushed offscreen, and the OS may reorder items — keep your single status item simple and don't rely on isVisible for logic.

## Recommendations
- Architecture: LSUIElement accessory app + one MenuBarExtra with .menuBarExtraStyle(.window) for the quick-glance popover (current temps, fan RPM, mode switcher), wrapped with orchetect/MenuBarExtraAccess for the isPresented binding and NSStatusItem handle; plus a single SwiftUI Window scene for the full dashboard opened via openWindow, toggling activation policy .accessory↔.regular on open/close. Put preferences inside the dashboard (tab or sheet) and do NOT ship a Settings scene — it sidesteps the openSettings breakage on Tahoe 26.
- Dynamic menu-bar readout: start with a plain Text label (e.g. '62° 3120') using .monospacedDigit() — this updates live and is zero-cost. If/when you add a sparkline in the menu bar, render it to an Image via ImageRenderer at NSScreen backingScaleFactor on each tick (cheap at 0.2–1 Hz); if you need variable-width or per-pixel control like Stats, switch that one surface to NSStatusItem + custom NSView (Stats' Kit/module/widget.swift is the blueprint) while keeping the rest SwiftUI.
- Polling engine: an actor or final class owning a DispatchSourceTimer on a .utility QoS serial queue, schedule(deadline:repeating: 1.0, leeway: .milliseconds(100)); do all IOKit/SMC reads there; publish an immutable SensorSnapshot struct to a @MainActor @Observable store. Drive cadence adaptively: 1 s when popover open or dashboard visible+non-occluded, 5 s when only the menu bar label is live, pause on screen sleep. This keeps the monitoring app itself from heating the machine it monitors.
- History & charts: fixed-capacity ring buffer per sensor (e.g. 3600 samples at 1 Hz = 1 h) stored as [SensorSnapshot] or a Deque; give Swift Charts a downsampled slice capped at ~500 points for the visible range; set explicit chartYScale domains (e.g. 0–100 °C, 0–max RPM); use if #available(macOS 15) { LinePlot(...) } else { LineMark ForEach } if you target 14.
- State: pure @Observable models everywhere, no Combine. One SensorStore (readings, history, fan state), one FanControlStore (mode, curve, target RPM), injected via .environment().
- Ship: SMAppService.mainApp toggle in preferences with live status readback and .requiresApproval deep-link; Sparkle 2 via SPM with SPUStandardUpdaterController, EdDSA keys, generate_appcast, appcast + zips on GitHub Releases; Developer ID + notarization (required anyway for a root fan-control helper).
- Set deployment target to macOS 14.0. It unlocks @Observable and all chart-interaction APIs, matches what Ice requires, and Ventura is security-EOL. Gate macOS 15 vectorized plots behind #available. Only consider a 15.0 floor if you decide vectorized plots and newer window-placement APIs are must-haves without fallbacks.

## Gotchas
- Never build live content on .menuBarExtraStyle(.menu): the run loop blocks while the menu is open, so RPM/temp rows freeze and cannot be updated or dismissed programmatically. Use .window style for any dynamic popover.
- MenuBarExtra .window style has real constraints: the panel is anchored to the status item with no repositioning control, is capped around half the screen width, cannot be detached, and MenuBarExtra offers no native right-click handling (apps like FontSwitch drop to AppKit for right-click menus). Plan the popover as a fixed-size, .frame()-bounded view.
- openSettings does not work on macOS Tahoe 26 and the hidden-window workaround is timing- and scene-order-sensitive (hidden Window scene must precede Settings scene; needs 100–200 ms delays). Avoiding the Settings scene entirely is the robust move.
- Activation-policy toggling has races: calling openWindow before the policy flip completes leaves the dashboard behind other windows and unable to become key. Sequence it: setActivationPolicy(.regular) → brief Task.sleep → openWindow → NSApp.activate.
- Swift Charts: a ForEach of LineMarks over an unbounded, ever-growing array is the classic mistake — UI becomes unresponsive within seconds of real-time updates (Apple forums 728636). Bound the buffer, downsample, fix axis domains, and avoid changing chart identity each tick.
- Repeating Timers without tolerance defeat macOS timer coalescing and measurably increase energy use — a thermal app that keeps the CPU awake is self-defeating. Always set leeway/tolerance and use .utility QoS, and don't poll from the main thread (IOKit calls can block for milliseconds).
- On Tahoe 26 the menu bar is transparent (Liquid Glass): non-template colored status icons look wrong against wallpaper; NSStatusItem.isVisible lies when the item is behind the notch/offscreen, so never gate polling on it — use popover/window visibility instead.
- MenuBarExtra label: don't fight it with fonts or arbitrary views — only Text and Image render, and font/symbol sizing is OS-controlled. ImageRenderer output must be generated at the screen's backing scale or the sparkline will be blurry; mark it as a template image where appropriate for Liquid Glass adaptation.
- SMAppService: users can silently remove the login item in System Settings, so a cached boolean in UserDefaults will drift from SMAppService.mainApp.status — always read status when rendering the toggle. Handle .requiresApproval (registration succeeded but user must approve in Login Items).
- Sparkle in a sandboxed app requires extra XPC configuration — but do not sandbox this app at all: SMC fan control needs a privileged helper (SMJobBless-era or SMAppService daemon) that is incompatible with the App Sandbox, which also rules out Mac App Store distribution and makes Sparkle the only sane update channel.
- Old advice that 'MenuBarExtra content doesn't update on @State change' (Apple forums thread 720625) refers to the .menu style's snapshot behavior in early Ventura; window-style content driven by @Observable models updates fine on macOS 14+ — don't cargo-cult EnvironmentObject workarounds from 2022 posts.

- [CONFIRMED] Opening the SwiftUI Settings scene from a menu bar app: private selectors showSettingsWindow:/showPreferencesWindow: stopped working in macOS 14 (Sonoma); SettingsLink is unreliable inside MenuBarExtra; the openSettings environment action works on macOS 15 but does NOT work on macOS 26 Tahoe; the working workaround requires a hidden Window scene declared BEFORE the Settings scene, activation-policy toggling (.accessory to .regular), and 100-200 ms delays — so the plan's choice to skip the Settings scene entirely is sound.
- [CONFIRMED] Stats (exelban/stats), the reference implementation for live menu-bar telemetry, uses NSStatusItem + custom NSView subclasses rather than MenuBarExtra: Kit/module/widget.swift defines a widget_t enum with chart/text widget cases, a WidgetWrapper NSView base class, and an SWidget class that calls NSStatusBar.system.statusItem(withLength:) and menuBarItem?.button?.addSubview(...), with a setWidth() resize callback.
  - CORRECTION: Minor detail: the widget_t enum's actual cases are unknown, mini, lineChart, barChart, pieChart, networkChart, speed, battery, batteryDetails, stack, memory, label, tachometer, state, text — there is no case literally named 'sensors' as the finding's example list implied (the multi-value widget is 'stack'). The architectural claim itself is accurate.
- [CONFIRMED] Launch-at-login via SMAppService.mainApp requires macOS 13+; register() and unregister() are throwing methods; there is a live status property with an SMAppService.Status enum including a .requiresApproval case ('registered, but the user needs to take action'); and a static openSystemSettingsLoginItems() method deep-links to the Login Items pane.
- [CONFIRMED] Vectorized Swift Charts plots (LinePlot) require macOS 15.0 / iOS 18.0 — so a macOS 14 deployment target must gate LinePlot behind #available(macOS 15) with a LineMark/ForEach fallback; LinePlot renders a whole collection of data (or a math function) as one plot instance.
