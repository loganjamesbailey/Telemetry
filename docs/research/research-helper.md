# helper

## Summary
The correct macOS 13+ architecture is: a non-sandboxed SwiftUI app that bundles a tiny root LaunchDaemon inside its own bundle (plist in Contents/Library/LaunchDaemons referencing the executable via BundleProgram), registered with SMAppService.daemon(plistName:) and approved once by the user in System Settings > General > Login Items & Extensions. The app talks to the daemon over NSXPCConnection to a launchd Mach service (declared in the plist's MachServices dict), and the daemon locks the connection down with -[NSXPCConnection setCodeSigningRequirement:] (macOS 13+) so only your signed app can call it — validated against the peer's audit token, never its PID. SMJobBless (deprecated macOS 13) and AuthorizationExecuteWithPrivileges (deprecated macOS 10.7) are obsolete; Quinn (Apple DTS) explicitly says "If you need ongoing privileges but don't want to ship an installer package, use SMAppService." For a free app: local development works with a free Apple ID's "Apple Development" certificate (both app and daemon MUST be signed with the same Apple-issued identity — ad-hoc "Sign to Run Locally" is explicitly unsupported and breaks background execution on restart), but public binary distribution realistically requires the $99 Developer ID + notarization; otherwise users must build from source or bypass Gatekeeper via System Settings (Sequoia+ removed the easy right-click-Open path). Proven real-world models: exelban/stats (fan control via eu.exelban.Stats.SMC.Helper, migrated SMJobBless→SMAppService in v3.0.2, and its CVE-2025-21606 is the canonical cautionary tale for skipping client validation), Karabiner-Elements v15 (production SMAppService daemons), agoodkind/macos-smc-fan (SMAppService+XPC three-tier design specifically for M1 fan control), and Apple's own sample attached to "Updating helper executables from earlier versions of macOS." The daemon should be a dead-man's-switch design: it owns fan state, requires periodic keepalives from the app, and autonomously restores SMC automatic fan mode on connection invalidation, missed keepalive deadline, system sleep, or its own termination path.

## Key facts
- Bundle layout (macOS 13+): daemon executable goes in the app bundle (e.g. Contents/MacOS/ or Contents/Library/HelperTools/), and its launchd plist goes in Contents/Library/LaunchDaemons/. Nothing is copied to /Library/LaunchDaemons or /Library/PrivilegedHelperTools anymore — the daemon runs directly out of the app bundle, so updating the app updates the daemon binary (source: Apple 'Updating helper executables from earlier versions of macOS', theevilbit.github.io/posts/smappservice, malpern/privileged_helper_help).
- Daemon plist required keys (verified working example from malpern/privileged_helper_help): Label (e.g. com.yourapp.helper), BundleProgram = 'Contents/MacOS/yourapp-helper' (path relative to the app bundle root), MachServices = { 'com.yourapp.helper.xpc': true }, AssociatedBundleIdentifiers = [main app bundle ID] (makes the Login Items entry display under your app's name).
- Registration API: let service = SMAppService.daemon(plistName: "com.yourapp.helper.plist") — the plistName MUST include the .plist extension or you get Error 108 'Unable to read plist'. Then try service.register(). Status enum: .notRegistered, .enabled, .requiresApproval, .notFound. SMAppService.openSystemSettingsLoginItems() deep-links the user to the approval pane.
- First-registration flow: register() typically throws 'Operation not permitted' (SMAppServiceErrorDomain Code=1) — this is EXPECTED, meaning approval is pending. The user must approve in System Settings > General > Login Items & Extensions and authenticate as admin (daemons require root). Once approved once, unregister()+register() cycles do NOT re-prompt for authentication (theevilbit blog, Apple forums thread 721919).
- Launch-on-demand: because the daemon declares MachServices, launchd starts it lazily on the first NSXPCConnection(machServiceName:) connect — it does not need KeepAlive=true and should not run permanently; Stats' helper exits itself (shouldQuit flag) when all XPC connections close.
- XPC lockdown (macOS 13+): in listener(_:shouldAcceptNewConnection:) call newConnection.setCodeSigningRequirement("anchor apple generic and identifier \"com.yourapp\" and certificate leaf[subject.OU] = \"YOURTEAMID\"") before resuming. This is Quinn's (Apple DTS) current recommendation (forums thread 681053); requirement syntax reference is TN3127 'Inside Code Signing: Requirements'. The C-API equivalents are xpc_connection_set_peer_code_signing_requirement (macOS 12+) and xpc_connection_set_peer_lightweight_code_requirement (macOS 14.4+). Since the target is macOS 26, setCodeSigningRequirement is always available.
- Never validate the peer by processIdentifier (PID) — PIDs are reusable and racing them is a known exploit primitive. Pre-13 code used the connection's audit token (private auditToken property) + SecCodeCopyGuestWithAttributes(kSecGuestAttributeAudit) + SecCodeCheckValidity; exelban/stats' fixed helper does exactly this (CodesignCheck.auditToken(for: connection) then codeSigningMatches(auditToken:)) in SMC/Helper/main.swift. setCodeSigningRequirement does this correctly for you.
- Cautionary tale — CVE-2025-21606 (exelban/stats ≤2.11.20, Critical): its shouldAcceptNewConnection unconditionally returned true, so ANY local process could call setFanMode/setFanSpeed as root, and its powermetrics method had a shell command injection = local privilege escalation to root. Fixed in v2.11.21 with audit-token code-signing validation. Design lesson: validate every connection AND never build shell strings in the daemon.
- Why not the old APIs (Quinn, 'BSD Privilege Escalation on macOS', forums thread 708765): AuthorizationExecuteWithPrivileges deprecated since macOS 10.7 — 'Do not use it in a widely distributed product'; SMJobSubmit deprecated 10.10; SMJobBless deprecated macOS 13 and replaced by SMAppService; 'Do not use a setuid-root executable. Ever.'; 'If you need ongoing privileges but don't want to ship an installer package, use SMAppService.' SMJobBless also required the legacy SMAuthorizedClients/SMPrivilegedExecutables Info.plist keys — including those keys in an SMAppService project actually causes Error 108 (malpern repo).
- Signing reality #1 (local dev, free Apple ID): app and daemon must both be signed with the SAME Apple-issued identity. Quinn verbatim: 'you should be signing both your embedded helper and your app with the same Apple-issued code-signing identity' and 'If... you are using ad hoc signing (Sign to Run Locally in Xcode parlance) then you will see problems like this' — including losing background-execution rights on every restart (forums thread 799910). Apple's SMAppService sample docs likewise say to use your Development signing certificate and that Sign to Run Locally is not supported (also because an ad-hoc cert chain can't be matched by a team-based code-signing requirement). A free Apple ID's Personal Team 'Apple Development' certificate IS an Apple-issued identity with a real Team ID, so free-account development-signed builds work on your own Mac.
- Signing reality #2 (distribution): notarization requires the paid $99/yr Apple Developer Program — free accounts are refused ('team is not enrolled in the Apple Developer Program'), and free accounts cannot create Developer ID certificates at all. On macOS Sequoia and later the control-click-Open Gatekeeper bypass is gone; users of an unsigned/unnotarized download must approve it in System Settings > Privacy & Security (or strip quarantine: xattr -cr). Open-source apps in this space (Stats, Karabiner-Elements) ship Developer ID-signed + notarized builds; the free-tier alternative is 'build from source with your own free cert' instructions, which conveniently also re-signs the daemon to the builder's identity.
- Real reference code: (1) Apple's official sample attached to developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos (a Quinn forum reply shows its daemon plist: BundleProgram => Contents/MacOS/DaemonSM, MachServices key == machServiceName string); (2) exelban/stats SMC/Helper/main.swift — NSXPCListener(machServiceName: "eu.exelban.Stats.SMC.Helper"), audit-token validation, protocol { setFanMode(id:mode:completion:), setFanSpeed(id:value:completion:), resetFanControl(completion:) }, serial smcQueue for SMC writes, self-terminates when connections close; (3) Karabiner-Elements v15 — production SMAppService daemons packaged in a dedicated 'Karabiner-Elements Privileged Daemons.app' with plists under its Contents/Library/LaunchDaemons, approval via Login Items & Extensions; (4) alienator88/HelperToolApp — minimal Swift SMAppService+XPC helper (helper in Contents/Library/HelperTools, plist in Contents/Library/LaunchDaemons); (5) agoodkind/macos-smc-fan — M1-specific research repo whose architecture is exactly ours: 'smcfan (CLI) → XPC → SMCFanHelper (privileged daemon) → IOKit → AppleSMC' via SMAppService, and documents that on Apple Silicon thermalmonitord enforces 'System Mode' (mode 3) so manual fan control needs an Ftst diagnostic-mode unlock sequence — i.e., on M1 the daemon must manage an unlock/relock lifecycle, raising the stakes for watchdog cleanup.
- Uninstall/cleanup: call service.unregister() (or the async variant) — the item disappears from launchctl and Login Items; because everything lives in the app bundle there are no orphan files to delete. Known OS bug: on macOS 13.6 the launchd job could keep running even after the user disabled the service (FB13206906, theevilbit). Dev troubleshooting tools: sfltool dumpbtm to inspect Background Task Management state, sfltool resetbtm to reset it when testing approval flows.
- Sandboxing: registering a daemon requires a non-sandboxed main app (fine — SMC/IOKit access rules out the Mac App Store anyway). Keep the daemon un-sandboxed too (it needs IOServiceOpen on AppleSMC); enable Hardened Runtime on both. Quinn's warning: code-signing-based client auth authenticates the process's main executable — if your app ever loads third-party plug-ins, the daemon can't distinguish them from your code.

## Recommendations
- Ship two targets: 'FanApp.app' (SwiftUI, menu-bar) and 'FanHelper' (plain Swift executable, no GUI frameworks — Quinn: never run GUI code as root). Embed FanHelper at Contents/MacOS/FanHelper (or Contents/Library/HelperTools/), plist at Contents/Library/LaunchDaemons/com.yourname.fanapp.helper.plist with Label, BundleProgram, MachServices={com.yourname.fanapp.helper.xpc:true}, AssociatedBundleIdentifiers=[com.yourname.fanapp]. Sign both with the same identity (free-account Apple Development for dev; Developer ID if/when you pay). Never ad-hoc sign.
- App-side install state machine (idempotent, run at every launch): switch service.status — .enabled: proceed; .notRegistered/.notFound: try register(), treat 'Operation not permitted' as approval-pending; .requiresApproval: show onboarding UI with a button calling SMAppService.openSystemSettingsLoginItems(). Re-run register() after app updates (safe once approved; no re-auth). Provide an explicit 'Uninstall helper' menu item that first tells the daemon to restore auto fan mode, then calls unregister().
- XPC protocol (@objc protocol FanHelperProtocol) — keep it tiny and fan-only, no generic command execution (the Stats CVE lesson): helperVersion(reply:(String)->Void); setFanTargetRPM(fanIndex:Int, rpm:Int, leaseSeconds:Int, reply:); setAutoMode(fanIndex:Int, reply:); keepalive(reply:); restoreAllAuto(reply:). Version every session: first call is helperVersion; if it doesn't match the app's bundled helper version constant, unregister()+register() to bounce launchd onto the new binary inside the updated bundle, then reconnect. Also set connection.remoteObjectInterface with explicit NSXPCInterface(with:) and keep all parameters primitive (Int/String) to avoid NSSecureCoding class-allowlist pitfalls.
- Daemon-side lockdown in listener(_:shouldAcceptNewConnection:): call newConnection.setCodeSigningRequirement("anchor apple generic and identifier \"com.yourname.fanapp\" and certificate leaf[subject.OU] = \"<TEAMID>\"") before resume(); generate the requirement string at build time from the signing settings so debug (Apple Development) and release (Developer ID) builds both match. Validate and clamp every RPM input against the fan's SMC-reported min/max in the daemon itself — never trust the client, even your own.
- Dead-man's-switch safety design (the daemon, not the app, owns safety): forced-RPM commands carry a lease (e.g. 30 s); the app's curve engine renews via keepalive every ~10 s; a DispatchSourceTimer in the daemon restores SMC auto mode the moment the lease expires, the NSXPCConnection invalidation/interruption handler fires (app crashed/quit), or the daemon receives a SIGTERM (install a sigterm DispatchSource that restores auto before exiting). Register IORegisterForSystemPower in the daemon and restore auto mode on kIOMessageSystemWillSleep, letting the app re-apply its curve after wake — note exelban/stats' shipped helper does NOT restore auto on disconnect (it just exits), which is a gap you should not copy, and on M1 the Ftst/System-Mode unlock (agoodkind/macos-smc-fan) makes relock-on-exit mandatory. Launch-on-demand via MachServices (no KeepAlive); daemon self-exits ~60 s after the last connection closes AND fans are back in auto — so the root process only exists while needed.
- Free-app distribution strategy: develop and use personally with a free Apple ID (Apple Development cert, works fully with SMAppService on your own machine). For public GitHub releases either (a) pay the $99 for Developer ID + notarytool — what Stats and Karabiner do and the only friction-free path on Sequoia/Tahoe, or (b) publish source with an xcodebuild script + instructions so users build/sign with their own free cert (this inherently satisfies the same-identity rule), documenting that a downloaded unsigned binary would require System Settings > Privacy & Security approval and would still hit the ad-hoc-signing daemon breakage — so distributing prebuilt ad-hoc binaries is NOT viable for this app; treat build-from-source as the free tier.
- Study these files before coding: Apple's sample from 'Updating helper executables from earlier versions of macOS' (canonical bundle layout + register flow), exelban/stats SMC/Helper/main.swift (audit-token validation + fan XPC methods + serial SMC write queue), alienator88/HelperToolApp (minimal modern skeleton), agoodkind/macos-smc-fan (M1 thermalmonitord System Mode/Ftst unlock and CLI→XPC→daemon→IOKit tiering), and TN3113 (XPC loopback testing — Quinn's advice: debug the XPC layer with an anonymous listener in-process before involving launchd at all).

## Gotchas
- plistName passed to SMAppService.daemon(plistName:) must include the '.plist' extension; omitting it yields Error 108 'Unable to read plist'. The same error appears if legacy SMJobBless keys (SMAuthorizedClients in the helper's Info.plist, SMPrivilegedExecutables in the app's) are present — delete them entirely.
- The first register() throwing 'Operation not permitted' is the SUCCESS path (approval pending), not a failure — don't surface it as an error; route the user to Login Items & Extensions instead. If the user dismisses the one-time system notification, re-registering does NOT re-post it; the only reliable path is openSystemSettingsLoginItems().
- Ad-hoc signing ('Sign to Run Locally') silently half-works then breaks: Quinn confirms you lose background-execution rights on every restart, and a team-based code-signing requirement can never match an ad-hoc peer. Every dev build must use a real Apple Development certificate, and app + daemon must share the identity — mismatched identities also caused daemons to show as 'Item from unidentified developer' and refuse to run on Sequoia (forums thread 757463).
- BundleProgram path, MachServices key, machServiceName in NSXPCListener/NSXPCConnection, Label, and the plist filename are five strings that must all be mutually consistent; any mismatch = daemon launches with status 78 (EX_CONFIG) or XPC calls that hang forever with no error (forums thread 799910). Add a 'first light' os_log at daemon main() to split config problems from code problems.
- Do not validate XPC peers by PID (race-condition LPE) and do not expose any 'run this command' method — CVE-2025-21606 in Stats chained exactly those two mistakes into root code execution. Also remember setCodeSigningRequirement authenticates the peer's main executable only; plug-in-loading clients defeat it.
- The daemon executes from inside the .app bundle: moving/deleting the app strands the launchd registration (status .notFound); Xcode DerivedData paths change, so during development the registered daemon can point at a stale build path — use sfltool resetbtm and re-register when the approval/registration state gets confused, and expect launchd to keep running an OLD daemon instance until unregister/kill even though the binary on disk is new (hence the helperVersion handshake).
- macOS 13.6 had a bug where disabling the service in System Settings didn't actually stop the launchd job (FB13206906) — one more reason the daemon must fail safe by itself (lease expiry → auto mode) rather than trusting the OS to stop it.
- Testing the approval UX from Xcode is awkward: each new signing identity/team change is a 'new' daemon requiring fresh approval, and the System Settings toggle state can lag; test the full flow from a /Applications-installed copy, not just Xcode's run destination.
- WebFetch note for the planning agent: developer.apple.com documentation pages render via JS and return near-empty content to fetchers — use the malpern/privileged_helper_help markdown mirror or Apple Developer Forums threads (which fetch fine) when you need Apple's exact wording.

## Verification
- [CONFIRMED] SMAppService daemon mechanics (macOS 13+): the daemon's launchd plist lives in the app bundle at Contents/Library/LaunchDaemons, BundleProgram is an app-bundle-relative executable path, registration is via SMAppService.daemon(plistName:), status enum is .notRegistered/.enabled/.requiresApproval/.notFound, SMAppService.openSystemSettingsLoginItems() opens the approval pane, and SMJobBless is deprecated in macOS 13 in favor of SMAppService.
  - CORRECTION: Every detail matches the macOS 26 SDK header verbatim. One nuance the findings underplay: the same header states 'Apps that contain LaunchDaemons must be notarized' (class-level discussion in SMAppService.h) — this sits in tension with the plan's assumption that a free-account Apple Development-signed build works fully on the developer's own Mac; Development-signed local registration is widely reported to work in practice, but the plan should not treat notarization as purely a distribution concern without testing. The header also confirms the findings' update advice: 'If an app updates either the plist or the executable... the SMAppService must be re-registered... recommended to also call unregister before re-registering if the executable has been changed.'
- [CONFIRMED] The daemon can restrict XPC callers to the signed app via -[NSXPCConnection setCodeSigningRequirement:], available since macOS 13.0, called in listener(_:shouldAcceptNewConnection:) before resuming the connection.
  - CORRECTION: API existence and availability confirmed directly in the SDK header: NSXPCConnection.h line 118 declares '- (void)setCodeSigningRequirement:(NSString *)requirement API_AVAILABLE(macos(13.0)) API_UNAVAILABLE(ios, tvos, watchos)'. On the target macOS 26 it is always available, so the pre-13 audit-token/SecCode fallback is unnecessary.
- [CONFIRMED] CVE-2025-21606 (exelban/stats <= 2.11.20, Critical): the fan helper's shouldAcceptNewConnection unconditionally returned true so any local process could drive setFanMode/setFanSpeed as root, plus a shell command injection in the powermetrics method enabled local privilege escalation; fixed in v2.11.21 with code-signing/audit-token validation.
  - CORRECTION: Confirmed exactly as stated; no correction needed.
- [CONFIRMED] exelban/stats' fixed helper (SMC/Helper/main.swift) is an accurate reference: NSXPCListener(machServiceName: "eu.exelban.Stats.SMC.Helper"), fan XPC methods setFanMode(id:mode:completion:)/setFanSpeed(id:value:completion:)/resetFanControl(completion:), peer validation via CodesignCheck.auditToken(for:) + codeSigningMatches(auditToken:), a serial smcQueue for SMC writes, and self-termination (shouldQuit) when all connections close.
